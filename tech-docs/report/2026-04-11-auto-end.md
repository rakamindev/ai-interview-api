## Overview

Auto-end triggers when all configured skills reach `covered` state. Rather than ending the session abruptly mid-audio, the system waits for the AI to finish speaking and for the frontend to drain its audio queue before closing the WebSocket and marking the session ended.

---

## 1. Coverage Detection (`AudioWebSocketMiddleware`)

### How it works

After each candidate turn, `refresh_coverage_cache` runs on a background thread and calls `Coverage::MapInjector#all_covered?`. When all configured skills are `covered` and no discovered skill is still `initiated`, the method returns true.

`all_covered?` is computed on the background thread and passed into an `EM.schedule` block to safely update WebSocket state on the EventMachine thread:

```ruby
EM.schedule do
  state.last_coverage_digest = fingerprint
  state.cached_coverage_text = text
  schedule_coverage_wrap_up(state, session) if all_covered
end
```

`schedule_coverage_wrap_up` sets `state.coverage_pending = true`. This flag is the single source of truth that auto-end should begin.

### Why not detect in the Sidekiq worker?

The worker (`CoverageAnalyzerWorker`) owns DB coverage updates but has no access to the browser WebSocket or Gemini client. Session lifecycle is owned by the middleware. Detecting and acting from the worker would require a cross-process callback, introducing race conditions with the existing middleware state machine.

## 2. Wrap-Up Signal Flow (`handle_coverage_auto_end`)

Called on every `on_model_turn_complete` when `coverage_pending = true`.

### Branch A — AI's last turn ended with a closing statement

```
AI: "Thank you for your time, you'll hear from us soon."
→ on_model_turn_complete → handle_coverage_auto_end
→ last_ai_turn_ends_with_question = false
→ preparing_to_end sent immediately
→ poll_for_session_end starts
```

No injection needed. The AI already closed naturally based on the coverage map.

### Branch B — AI's last turn ended with a question

```
AI: "How would you handle that at scale?"
→ on_model_turn_complete → handle_coverage_auto_end
→ last_ai_turn_ends_with_question = true
→ waiting_for_candidate_response = true
→ 20s fallback timer starts (no injection yet)
```

The system waits for the candidate to answer the question. On the candidate's next turn (`on_input_transcription`), the wrap-up signal is piggybacked on the coverage map injection:

```ruby
if state.waiting_for_candidate_response && !state.wrap_up_injected
  gemini_ref.inject_context(wrap_up_signal)
  state.wrap_up_injected = true
  state.waiting_for_candidate_response = false
  state.coverage_end_timer&.cancel
end
```

The AI's response to the candidate's answer — with the wrap-up signal in context — is the closing statement.

**20s fallback:** If the candidate stays silent, the timer fires and injects the wrap-up signal directly so the AI closes via the silence pump.

### Branch C — Phase 2 (after wrap-up injected)

When `wrap_up_injected = true`, the next `on_model_turn_complete` (AI's closing turn) triggers:

```
→ preparing_to_end sent to frontend
→ poll_for_session_end starts
```

### Detection: question vs. closing

```ruby
state.last_ai_turn_ends_with_question = text.rstrip.end_with?('?')
```

Set in `on_output_transcription` after stripping metadata. Universal across all languages — no keyword matching required.

## 3. Frontend Coordination (`audio_complete` API)

### Why a REST endpoint instead of ending directly from WebSocket

The WebSocket's `on_model_turn_complete` fires when all audio **frames have been sent** to the browser — not when the browser has finished **playing** them. Ending the session immediately would close the WebSocket while audio is still queued in the browser's audio context, cutting off the AI's closing speech mid-sentence.

### Flow

```
Backend WS                    Frontend                     Backend HTTP
     │                            │                              │
     │── preparing_to_end ───────►│                              │
     │                            │  (mute mic, stop sending)    │
     │                            │  waitForDrain()              │
     │    AI closing audio ───────►│  (plays out all audio)       │
     │                            │                              │
     │                            │── POST /sessions/:token/ ───►│
     │                            │        audio_complete        │
     │                            │                              │  EndHandler.call
     │                            │◄── { ended: true } ─────────│  (session marked ended)
     │                            │                              │
     │  poll detects ended ───────►                              │
     │── session_ended ──────────►│                              │
     │  (300ms delay)             │  show Interview Complete     │
     │  browser_ws.close          │                              │
```

### `waitForDrain` (frontend)

Polls every 250ms until `ctx.currentTime >= nextPlayTime`, where `nextPlayTime` is the **end timestamp** of the last enqueued audio frame. Checks synchronously on first call — resolves immediately if queue is already empty. Fires a 10s safety timeout in case the audio context stalls.

### `poll_for_session_end` (backend)

Polls `session.reload.ended?` every 1 second for up to 30 attempts. On detection, calls `close_session_after_end` which sends `session_ended` then closes the WebSocket after a 300ms delay (gives browser time to process the message before the `onclose` event fires).

After 30 attempts (30s) without a signal, the backend calls `Sessions::EndHandler` directly as a fallback — the session always ends even if the frontend never calls `audio_complete`.

### `audio_complete` endpoint

```
POST /api/v1/sessions/:token/audio_complete
Auth: invite token in URL (no JWT — candidate-facing)
```

Does **not** re-check `all_covered?`. The backend WS already verified coverage before sending `preparing_to_end`. Re-checking caused false negatives due to the timing gap between WS detection and HTTP call arrival, stalling auto-end.

## 4. System Prompt Change (Rule 7)

**Before:**
> When all skills are covered OR when you receive a time warning: First, react to the candidate's last answer naturally (brief acknowledgment). Then close with a warm statement.

**Problem:** "React naturally" was interpreted by the AI as including a follow-up question. The AI would ask one more question then close — the question was never answered because the wrap-up signal triggered an immediate response via the silence pump.

**After:**
> When you receive `{ "wrap_up": true }` in a TIME CONTROL message, you MUST close the interview immediately. The very next words out of your mouth must BEGIN the closing — not a question, not a probe, not a bridge. DO NOT ask ANY question of any kind.

## 5. Coverage WebSocket Auth Fix

The assessor live monitor connects via `WS /ws/sessions/:id/coverage`. The browser cannot set `Authorization` headers on WebSocket connections, so the frontend sends:

```json
{ "type": "auth", "token": "<JWT>" }
```

as the first message after connect.

**Before:** The middleware only authenticated in `on :open` from the `HTTP_AUTHORIZATION` header. With no header, auth failed and the connection closed immediately — the assessor saw a "Reconnecting..." loop.

**Fix:** The middleware now supports two auth paths:
1. `on :open` — JWT in `Authorization` header (existing, kept for non-browser clients)
2. `on :message` — `{ type: "auth", token }` message after connect (new, for browser clients)

Auth is deferred until the message arrives. `send_current_state` and `subscribe_to_coverage_updates` are called after either path succeeds.

## Pros and Cons

### Pros

**Clean audio cutoff.** The session ends only after the frontend confirms audio playback is complete. The candidate always hears the full closing statement.

**Candidate gets to answer the last question.** When the AI asks a question as its final turn before coverage is detected, the system waits for the candidate's response before injecting the wrap-up. The AI's response to that answer is the closing — not a jarring mid-question shutdown.

**No dependency on AI turn count.** The system branches on whether the AI's last turn was a question or a closing statement, rather than counting turns or applying fixed delays.

**Always terminates.** Three independent fallbacks guarantee the session always ends:
1. Frontend calls `audio_complete` → session ends via HTTP
2. `poll_for_session_end` fallback after 30s → session ends directly from WS
3. 20s fallback timer → wrap-up injected if candidate goes silent

**Assessor-side end still works.** `POST /sessions/:id/end_session` (assessor-facing, JWT auth) bypasses the whole flow and ends immediately. The manual end path is independent.

### Cons

**One extra question before auto-end.** The AI generates its final probing question before `all_covered` is detected because `CoverageAnalyzerWorker` runs asynchronously (Sidekiq) after the candidate turn. The coverage state used for injection during a candidate turn reflects the **previous** turn's analysis. There is always a one-turn lag between the last skill being covered and the AI knowing to close.

**Inherent to async coverage analysis.** Fixing this would require running coverage analysis synchronously within the candidate turn — before the AI generates its response — which would add latency to every single turn for the sake of the last one.

**`waiting_for_candidate_response` state is not persisted.** If the browser WebSocket disconnects and reconnects while in this state, a new `ConnectionState` is created with `waiting_for_candidate_response = false`. The session would continue as normal — the candidate would need to speak again to trigger the next coverage check cycle. The session will still eventually end via the time ceiling or assessor manual end.

**AI double-close edge case.** If the AI closes naturally on its own (based on coverage map) AND the wrap-up signal is also injected (because `wrap_up_injected` was set before the natural close was detected), the AI may deliver two closing statements. Mitigated by the `?` detection branch: if the AI's last turn did not end with a question, no injection is made.
